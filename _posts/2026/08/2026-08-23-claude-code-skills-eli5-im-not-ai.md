이 블로그에 발행된 글은 209개입니다. 그중 몇 개가 AI가 쓴 것처럼 읽히는지는 한 번도 세어본 적이 없었습니다. 감으로는 "몇 개 있겠지" 수준이었고, 그 감을 검증할 수단도 없었습니다.

Claude Code 스킬 두 개를 설치해서 그 숫자를 냈습니다. 하나는 모르는 주제를 그림으로 설명받는 `eli5`, 다른 하나는 한글 AI 티를 카테고리로 분류해 잡아내는 `im-not-ai`입니다. 두 스킬의 구조를 먼저 정리하고, 뒤쪽에서 209개 글에 실제로 돌린 결과를 보겠습니다.

---

## 1. 설치

두 스킬 모두 Claude Code 플러그인 마켓플레이스로 설치합니다. 저장소를 클론하지 않아도 됩니다.

```bash
# eli5 - Anthropic이 운영하는 커뮤니티 마켓플레이스
claude plugin marketplace add anthropics/claude-plugins-community
claude plugin install eli5@claude-community

# im-not-ai - 저장소 자체가 마켓플레이스
claude plugin marketplace add epoko77-ai/im-not-ai
claude plugin install humanize-korean@im-not-ai
```

Claude Code 세션 안이라면 `claude plugin` 대신 `/plugin` 슬래시 명령을 씁니다. 설치 확인은 아래와 같습니다.

```bash
claude plugin list
```

```text
  eli5@claude-community
    Version: 1.0.0
    Scope: user
    Status: enabled

  humanize-korean@im-not-ai
    Version: 2.3.2
    Scope: user
    Status: enabled
```

설치된 실체는 `~/.claude/plugins/cache/<marketplace>/<plugin>/<version>/` 아래에 그대로 놓입니다. 스킬 본문과 참조 파일을 직접 읽어볼 수 있어서, 무엇을 하는 스킬인지 확인하려면 이 경로를 여는 편이 설명 문서보다 빠릅니다.

새 세션부터 스킬이 로드됩니다. 설치한 세션에서는 아직 잡히지 않습니다.

## 2. eli5

`eli5`는 모르는 주제를 큰 그림과 적은 단어로 설명하는 HTML 아티팩트를 만듭니다. `/eli5 <주제>` 형태로 호출합니다.

```text
/eli5 how does DNS work
```

이 스킬이 흥미로운 이유는 크기입니다. `SKILL.md` 본문 전체가 아래 세 줄입니다.

```markdown
Explain like I'm someone who knows nothing about this topic,
using a HTML artifact with big pictures and few words.

Topic: $ARGUMENTS
```

frontmatter의 `description`까지 합쳐도 열 줄이 안 됩니다. 모델에 새 능력을 붙이는 코드가 없고, MCP 서버도 없고, 스크립트도 없습니다.

그래서 이 스킬이 실제로 고정하는 것은 능력이 아니라 **출력 형식과 청자 수준** 두 가지입니다. 같은 질문을 그냥 던지면 답변은 문단과 불릿으로 나오고, 설명 수준은 질문한 사람이 이미 그 분야를 안다고 가정한 쪽으로 기울기 쉽습니다. `eli5`는 "아무것도 모르는 사람"과 "HTML 그림"을 매번 강제해서 그 기울기를 없앱니다.

쓰면서 유용했던 자리와 아니었던 자리가 갈립니다.

- 처음 보는 프로토콜이나 서비스의 큰 흐름을 잡을 때 유용하다
- 남에게 설명할 자료의 초안이 필요할 때 유용하다
- 이미 아는 주제에는 낭비다. 아는 내용을 다시 크게 그려주기만 한다
- 정확성 검증 장치가 없다. 산출물은 근거가 붙은 문서가 아니라 설명용 그림이다

세 줄짜리 스킬이 쓸모 있다는 사실 자체가 스킬의 성격을 보여줍니다. 스킬은 기능 추가가 아니라 기본 동작을 특정 방향으로 눌러두는 장치입니다.

## 3. im-not-ai

`im-not-ai`는 반대쪽 극단입니다. 스킬 하나에 참조 파일 12개, 에이전트 정의 9개, 파이썬 스크립트 14개가 딸려 있습니다.

목표는 한 줄로 요약됩니다. AI가 쓴 한글에서 **내용은 건드리지 않고 문체와 리듬만** 사람이 쓴 한국어로 되돌립니다.

### 3.1. 왜 한글 전용인가

영어권 humanizer가 한국어에 약한 이유는 한글 AI 글의 티가 대부분 영어 번역투에서 나오기 때문입니다. 영어 문장 구조를 한글 조사로 옮긴 흔적이 남습니다.

| 번역투 | 자연스러운 한국어 |
|---|---|
| AI 기술을 통해 효율을 높일 수 있다 | AI로 효율을 높인다 |
| 이에 있어서 중요한 점은 | 여기서 중요한 건 |
| ~에 의해 생성된 | ~가 만든 |
| 결론적으로, 이는 시사하는 바가 크다 | (삭제) |

이 스킬은 그 패턴을 10대 카테고리 아래 70개 서브 패턴으로 정리해 SSOT 파일 하나로 관리합니다.

| ID | 대분류 | 대표 패턴 |
|---|---|---|
| A | 번역투 | ~를 통해, ~에 있어서, 이중 피동 ~되어진다, 이중 조사 ~에서의 |
| B | 영어 인용 과다 | 과도한 괄호 병기, 번역 가능한 영어를 그대로 둠 |
| C | 구조적 AI 패턴 | 기계적 첫째 둘째 셋째, 과도한 불릿과 이모지, 대구 병렬 |
| D | AI 특유 관용구 | 결론적으로, 시사하는 바가 크다, 주목할 만하다 |
| E | 리듬 균일성 | 문장 길이 편차 낮음, 동일 종결어미 반복 |
| F | 수식 중복 | 매우, 정말, 동의어 이중 수식 |
| G | Hedging 남용 | ~할 수 있을 것으로 보인다 |
| H | 접속사 남발 | 문두 또한, 따라서, 즉의 연속 |
| I | 형식명사 과다 | 것이다, 점, 수, ~할 필요가 있다 |
| J | 시각 장식 남용 | 과도한 볼드, 대시 남발 |

패턴마다 심각도가 붙습니다. S1은 한 번만 나와도 AI로 확신하는 것이라 무조건 제거하고, S2는 1회에서 2회까지 허용하되 3회 이상 반복되면 제거하며, S3는 다른 패턴과 겹칠 때만 문제로 봅니다.

### 3.2. 의미를 지키는 장치

윤문 도구에서 실제 위험은 티를 못 잡는 쪽이 아니라 문장을 다듬다가 주장을 바꿔버리는 쪽입니다. 이 스킬은 그 위험에 네 가지 제약을 걸어둡니다.

- 의미 불변: 사실, 수치, 고유명사, 직접 인용은 원문 그대로 보존한다
- 근거 기반: 탐지된 span에만 수정한다. 탐지 없는 구간은 건드리지 않는다
- 장르 유지: 칼럼을 문학으로, 리포트를 에세이로 옮기지 않는다
- 과윤문 금지: 변경률 30%를 넘으면 경고하고 50%를 넘으면 강제 중단한다

마지막 항목이 특히 중요합니다. 변경률 판정을 모델의 자기 보고가 아니라 파이썬 스크립트가 합니다. 모델에게 "많이 고쳤니?"를 묻지 않고 코드가 문자열을 비교합니다.

## 4. 점수가 경로를 정하고 경로가 콜 수를 정한다

`im-not-ai`의 v2.2에서 들어온 구조가 `route_hint`입니다. 이 부분이 스킬 설계로서 가장 참고할 만합니다.

![route_hint가 결정적 점수로 경로를 고르고 경로가 LLM 콜 수를 정하는 흐름](/assets/img/ai/humanize/humanize-route-hint.webp)

입력이 들어오면 LLM이 아니라 파이썬 shim이 먼저 글을 읽습니다. `prepare_monolith_input.py`가 카운트형 지표와 위험 등급을 산출하고, 그 점수로 경로를 결정합니다.

| 경로 | LLM 콜 수 | 조건 | 파이프라인 |
|---|---|---|---|
| light | 1 | 카운트형 티 2건 이하, 위험 등급 낮음 | 진단과 finalize 생략, 보수적 윤문 한 번 |
| standard | 2 | 티가 섞여 있거나 구조 지표로 위험 높음 | 진단 한 번, 겨냥 윤문 한 번 |
| heavy | 3 이상 | 티 8건 이상 밀집, 또는 15000자 초과 | 진단, 윤문, finalize |

판정에 쓰는 지표는 전부 정수 카운트입니다. 마무리 관용구 수, 이중 피동 수, `가지고 있다` 같은 직역 표현 수, 이중 조사 수를 셉니다. 밀도나 z-score 같은 상대 지표는 판정에서 빼두었는데, 저장소가 밝힌 이유는 v2 baseline이 아직 placeholder라 불안정하다는 것입니다. 자기 지표의 신뢰 구간을 알고 그만큼만 쓰는 설계입니다.

절감은 모델을 싼 것으로 바꿔서 나오지 않습니다. 콜 수를 줄여서 나옵니다. 잘 쓴 글에 최중량 파이프라인을 돌리던 낭비가 `route_hint`에서 걸립니다.

저장소가 근거로 든 실측 하나는 청킹에 관한 것입니다. 1만자 글을 7개 청크로 쪼개 돌리면 610K 토큰, 단일 콜로 돌리면 134K 토큰이었고 품질은 동등했습니다. 청크마다 룰북과 진단을 다시 로드하는 비용이 병렬화 이득을 전부 먹었기 때문입니다. 그래서 이 스킬은 청킹을 heavy 경로 전용으로 두고 15000자 이하에는 권장하지 않습니다.

윤문본이 나오면 `verify_gates.py`가 네 축을 검사합니다. 문자 기준 변경률, S1 목표 달성, 대구 전멸 여부, 수치와 golden 문구 보존입니다. 문자 변경률만 보면 구조 편집을 놓치기 때문에 축을 더 둔 것인데, 저장소가 든 예는 변경률 2.77% 뒤에 문장 터치율 29.7%와 대구 75% 감소가 숨어 있던 사례입니다.

## 5. 발행된 글 209개에 돌려보기

여기까지가 스킬 설명이고, 이제 실제로 돌린 결과입니다.

![209개 글을 결정적 점수로 분류해 24개만 LLM 윤문 대상으로 남기는 흐름](/assets/img/ai/humanize/humanize-blog-triage.webp)

### 5.1. 스캔 방법

209개 글에 전부 LLM 윤문을 돌리면 비용이 터집니다. 그래서 `route_hint`를 산출하는 부분만 떼어내 전수 스캔에 썼습니다. 이 단계는 파이썬만 돌기 때문에 LLM 콜이 0입니다.

한 가지 전처리가 필요했습니다. 기술 블로그 글은 본문의 상당 부분이 코드 블록, 명령어 출력, YAML입니다. 이것을 그대로 채점하면 지표가 코드에 오염됩니다. `가지고 있다`를 세는 지표에 셸 스크립트가 섞이면 의미가 없습니다. 그래서 frontmatter, 펜스 코드 블록, 인라인 백틱, 이미지, kramdown 속성, 고정 footer를 제거한 산문만 점수 대상으로 두었습니다.

```python
m = metrics_v2.compute_all_v2(prose, genre="blog")
hint = compute_route_hint(m)
```

### 5.2. 결과

| 경로 | 글 수 | 뜻 |
|---|---|---|
| light | 184 | 카운트형 티 2건 이하. 손댈 것이 거의 없다 |
| standard | 21 | 티가 섞여 있다. 진단과 윤문 대상 |
| heavy | 4 | 15000자 초과 |

88%가 light로 나왔습니다. 지표 하나짜리 결과라 "AI 티가 없다"는 증명은 아니지만, 전수 스캔이 비용 없이 우선순위를 정해준다는 점은 분명합니다.

카운트형 티가 가장 많이 잡힌 글은 아래와 같습니다.

| 글 | 산문 길이 | 카운트형 티 | 지배 지표 |
|---|---|---|---|
| GCP 리소스 계층 | 8826자 | 6건 | 마무리 관용구 4, 안전 대구 2 |
| ArgoCD RBAC | 9641자 | 4건 | 마무리 관용구 4 |
| AWS Lake Formation | 10259자 | 4건 | 마무리 관용구 4, 대구 7 |
| Bedrock KB 챗봇 | 20930자 | 3건 | 직역 표현 2, 대구 9 |

한 패턴이 압도적이었습니다. `결론적으로`, `정리하면` 같은 마무리 관용구입니다. 글 하나에 3개에서 4개가 몰려 있는 경우가 많았고, 대체로 각 H2 섹션의 마지막 문단이 같은 방식으로 끝나 있었습니다. 섹션마다 요약 문단을 붙이는 습관이 지표로 잡힌 것입니다.

두 번째는 대구 병렬입니다. `A가 아니라 B다`, `X는 Y하고 Z는 W한다` 형태로 문장이 대칭을 이루는 패턴이 Lake Formation 글에서 7개, Bedrock 글에서 9개 나왔습니다. 한두 개는 수사지만 한 글에 아홉 개가 있으면 리듬이 기계적으로 들립니다.

### 5.3. 결과를 그대로 믿으면 안 되는 지점

heavy로 분류된 4개는 AI 슬롭이 밀집한 글이 아닙니다. 전부 15000자 초과 조건에 먼저 걸린 결과이고, 카운트형 티는 1건에서 3건입니다. 오히려 그중 하나는 위험 등급이 낮음입니다. `route_hint`의 heavy는 "심각하다"가 아니라 "콜을 더 써도 되는 분량이다"에 가깝습니다.

반대 방향 오독도 있었습니다. 771자짜리 독서 기록 글이 위험 등급 높음으로 나왔는데 카운트형 티는 0건이었습니다. 짧은 글에서는 문장 수가 적어 리듬 지표의 분산이 튑니다. 이 글은 사람이 직접 쓴 개인 기록이라 윤문 대상에서 뺐습니다.

### 5.4. 발행된 글에 적용할 때 바꾼 것

스킬의 기본 동작은 입력 텍스트를 받아 `final.md`를 새로 쓰는 것입니다. 이미 발행된 Jekyll 글에는 그대로 쓸 수 없었습니다. 파일 전체를 재작성하면 코드 블록, frontmatter, 이미지 경로, 고정 footer, Reference 링크가 모델 출력에 실려 나갑니다.

그래서 산출물 형태만 바꿨습니다. 진단은 스킬의 룰북과 taxonomy를 그대로 쓰고, 적용은 Edit 단위 수술적 수정으로 제한했습니다. 아래는 절대 건드리지 않는 목록입니다.

- frontmatter 전체
- 펜스 코드 블록 안의 모든 줄과 인라인 백틱
- URL, 링크 타겟, 이미지 경로, Reference 섹션
- 숫자, 버전, 고유명사, 명령어, 파일 경로
- 고정 footer 블록
- 스크립트가 관리하는 H2 번호 접두사

블로그 자체 규칙과 스킬 룰북이 충돌하는 지점도 있었습니다. 이 저장소는 middle dot과 arrow 문자를 금지하고, 본문 문단은 존댓말, 목록과 표 셀은 짧은 평서체로 고정합니다. 룰북에는 이 규칙이 없으니 윤문 지시에 명시적으로 넣어야 합니다. 저장소별 문체 규칙이 있으면 스킬 룰북보다 위에 두는 편이 맞습니다.

기존 [Agentic Development Environment 글](/posts/building-an-agentic-development-environment/)에서 정리한 원칙과 같습니다. 에이전트에게 넘기는 작업은 산출물 형태와 금지 목록을 먼저 못 박아야 검토 비용이 줄어듭니다.

## 6. 쓰면서 걸린 것

두 스킬 모두 만족스러웠지만 한계는 분명합니다.

`eli5`는 검증 장치가 없습니다. 그림은 설득력 있게 나오는데 그 안의 내용이 맞는지는 아무도 확인하지 않습니다. 모르는 주제의 큰 그림을 잡는 용도까지가 안전한 범위이고, 그 그림을 근거로 판단하려면 별도 확인이 필요합니다.

`im-not-ai`는 지표의 성격을 알고 써야 합니다. 카운트형 지표는 안정적이지만 그것만으로는 티의 절반만 봅니다. 리듬 균일성이나 형식명사 과다처럼 카운트가 안 되는 패턴은 결국 모델 진단에 맡겨야 하고, 그 판정은 회차마다 흔들립니다. 저장소가 옛 5인 파이프라인을 은퇴시킨 이유로 든 것도 span 열거가 0에서 18까지 요동쳤다는 점이었습니다.

지표가 인용을 구분하지 못하는 문제도 있습니다. 이 글을 같은 스캐너에 넣으면 카운트형 티가 6건 나옵니다. 전부 위 카테고리 표에 예시로 적어둔 `결론적으로`, `되어진다`, `~에서의` 같은 문구입니다. 어휘 카운트 방식이라 인용인지 실제 사용인지 가리지 못합니다. AI 티를 다루는 글이 스스로 AI 티 판정을 받는 구조인데, 이 글에서 실제로 고칠 것으로 잡힌 것은 `결정을 내리려면` 한 곳뿐이었습니다.

그리고 사람이 직접 쓴 글을 윤문 대상에 넣으면 안 됩니다. 개인 회고, 실습 기록, 구어체 메모는 리듬이 불규칙해서 지표상 튈 수 있는데, 그 불규칙성이 사람이 쓴 증거입니다. 이 블로그도 학습 시리즈 일부와 개인 기록을 명시적으로 제외 목록에 두고 있습니다.

정리 대신 실제로 남은 것을 적으면, 스캔은 209개 전수로 돌릴 만한 비용이었고 윤문은 25개 남짓에만 쓸 가치가 있었습니다. 그 비율을 결정적 코드가 정해준다는 점이 이 스킬의 핵심입니다.
