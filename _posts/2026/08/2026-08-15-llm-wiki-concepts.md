회의록은 회의가 끝나면 다시 읽히지 않는다. runbook은 장애가 나야 열리고, 프로젝트 회고는 다음 프로젝트가 시작될 때 이미 어딘가로 사라졌다. 그래서 조직마다 "지식을 남기자"는 시도가 반복되지만, 남은 문서는 결국 사람이 다시 읽어야 정보가 된다. AI 에이전트를 업무에 쓰기 시작하면 이 문제가 한 단계 심해진다. 사람조차 안 읽는 문서를 모델은 더 읽지 못한다.

LLM Wiki는 이 지점에서 출발한다. 문서를 사람이 읽는 형태에서, **사람과 LLM이 같이 읽는 형태**로 바꾸는 지식 베이스 설계다.

---

## 1. 왜 일반 위키로는 부족한가

Confluence나 Notion 같은 위키는 사람 독자를 전제로 설계되었다. 화면 UI에서 읽고, 하이퍼링크를 클릭하고, 검색창에 키워드를 넣는다. 이 구조가 LLM 앞에서 무너지는 지점은 세 가지다.

첫째, **컨텍스트 윈도우는 유한하다**. 문서가 600개라고 전부 프롬프트에 넣을 수는 없다. 토큰 비용과 응답 지연이 늘고, 관련 없는 문서가 섞이면 오히려 답변 품질이 떨어진다. 모델이 필요한 순간에 필요한 문서만 찾아 갖고 올 수 있어야 한다.

둘째, **맥락이 문서 안에 없다**. 회의록에 "지난번 결정대로 진행하기로 했다"라고 적혀 있으면 사람은 어느 결정인지 검색해서 찾는다. LLM도 마찬가지로 저 링크를 따라갈 수 있어야 하는데, 일반 위키의 문서는 이런 연결이 암묵적이거나 UI 클릭에만 존재한다.

셋째, **갱신 주기가 다르다**. 사람이 읽는 위키는 조금 오래돼도 큰 문제가 없다. 읽는 사람이 상식으로 보정한다. LLM은 오래된 문서와 최신 문서를 구분하지 못한 채 둘 다 사실로 답한다. 그래서 문서마다 갱신 시점과 신뢰도가 기계적으로 표시돼야 한다.

## 2. LLM Wiki의 정의

LLM Wiki는 **LLM이 질의 시점에 검색해 읽을 수 있게 구조화된 마크다운 지식 베이스**다. Karpathy가 2026년 초에 제안한 패턴으로, 핵심 주장은 단순하다. 지식을 매번 모델이 다시 유추하게 하지 말고, **섭취(ingest) 시점에 한 번 정리해서 위키로 컴파일**하라는 것이다.

이 관점에서 RAG와 LLM Wiki를 나눠 볼 수 있다. RAG는 원문 코퍼스를 그대로 두고 질의 시점에 검색해 조각을 가져온다. 원문은 흩어져 있고, 정리는 질의할 때마다 모델에게 맡긴다. LLM Wiki는 그 반대다. 섭취 시점에 사람과 에이전트가 원문을 정리해 교차 참조와 모순 표시가 박힌 문서로 만들어 둔다. 질의 시점에는 검색만 하면 된다.

| 구분 | RAG | LLM Wiki |
|---|---|---|
| 정리 시점 | 질의할 때마다 | 섭취할 때 한 번 |
| 원문 상태 | 흩어진 원문 그대로 | 정리된 문서로 컴파일 |
| 문서 간 연결 | 검색 결과로만 만나는 조각 | 위키링크로 미리 연결 |
| 모순 처리 | 모델이 그때그때 판단 | 문서에 모순 표시로 남음 |
| 갱신 | 원문 교체 | 문서 갱신 + 이력 기록 |

둘은 대체재가 아니라 계층이다. RAG가 원문 검색 계층이라면 LLM Wiki는 그 위에 있는 정리된 지식 계층이다.

## 3. 왜 마크다운이고 왜 파일인가

LLM Wiki의 기본 재료는 데이터베이스가 아니라 **평범한 마크다운 파일**이다. 이 선택에는 이유가 있다.

첫째, 토큰 효율. 마크다운은 텍스트 그 자체라 HTML이나 JSON보다 같은 정보에 토큰이 적게 든다. 태그가 곧 노이즈가 되는 LLM 입력에서 이건 비용 문제다.

둘째, 도구 독립성. 파일이면 git으로 버전 관리가 되고, grep으로 찾을 수 있고, 어떤 에디터로도 열 수 있다. 특정 SaaS가 서비스를 종료해도 지식은 남는다. Obsidian 같은 툴은 이 파일 묶음을 UI로 보여주는 뷰어일 뿐이다.

셋째, LLM 친화 메타데이터. 각 문서는 YAML frontmatter로 제목, 갱신일, 신뢰도를 달 수 있다. 사람 눈에는 잡아먹히지 않지만 에이전트는 이 메타데이터로 "이 문서는 3개월 됐고 신뢰도 medium이다"를 기계적으로 판단한다.

## 4. 구조의 뼈대

운영 중인 LLM Wiki의 디렉터리를 들여다보면 대략 이런 뼈대가 나온다.

```
wiki/
  index.md          # 전체 문서의 목차
  log.md            # 위키 변경 이력
  SCHEMA.md         # 이 위키의 규칙
  concepts/         # 재사용 가능한 개념 문서
  runbooks/         # 운영 절차 문서
  queries/          # 질의 결과를 남긴 문서
  raw/              # 원문 스냅샷 (수정 금지)
  evaluations/      # 검색 품질 측정 기록
  goals/            # 목표 관련 문서
```

각 파일은 frontmatter와 본문, 위키링크로 이뤄진다.

```markdown
---
title: 쿠버네티스 어드미션 컨트롤
created: 2026-05-02
updated: 2026-08-01
type: concept
tags: [kubernetes, security]
sources: [k8s-docs]
source_status: official
confidence: high
---

# 쿠버네티스 어드미션 컨트롤

... 본문 ...

관련: [[pod-security-admission]], [[kubernetes-api-server]]
```

여기서 중요한 규칙이 몇 개 있다. `[[위키링크]]`는 반드시 실제 파일로 풀려야 하고 깨진 링크는 커밋 게이트에서 막는다. 원문은 `raw/`에 불변으로 보존하고 정리본에만 손을 댄다. 의미 있는 변경은 `log.md`에 한 줄씩 남긴다. 문서 이름은 소문자-하이픈으로 통일한다. 이 규칙들이 사람이 다 안 지켜도 **에이전트가 지키도록 스크립트로 강제**할 수 있다는 게 LLM Wiki의 차별점이다.

## 5. 사람 위키와 다른 점 세 가지

정리하면 LLM Wiki는 기존 위키에 다음을 더한다.

**첫째, 검색 계층이 명시적이다.** 사람 위키의 검색은 UI 부가기능이지만 LLM Wiki에서는 본체다. BM25 같은 키워드 검색과 임베딩 검색을 조합한 하이브리드 검색, 그리고 그 품질을 측정하는 평가셋이 위키의 일부로 존재한다. 검색이 나빠지면 지식이 있어도 못 쓰는 것과 같기 때문이다.

**둘째, 갱신이 이벤트가 아니라 파이프라인이다.** 새 문서가 들어오면 분류하고, 링크를 걸고, 인덱스에 등록하는 작업이 사람의 기억이 아니라 절차로 돈다. 이 파이프라인의 상태가 곧 위키의 건강 상태다.

**셋째, 신뢰도가 문서 단위로 관리된다.** 공식 문서에서 온 건지, 실험 결과인지, 추측인지를 frontmatter의 `source_status`와 `confidence`로 구분한다. LLM이 근거 없는 답을 했을 때 "어떤 문서를 근거로 답했는지" 역추적할 수 있는 구조다.
